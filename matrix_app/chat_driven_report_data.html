Feeding the template reskin from /api/chat

Right now the custom-template flow gets its data from one fixed MySQL lookup keyed by a topic_id. The plan below swaps that single source for a free-text question answered by the existing chat agent — everything downstream of the data (the LLM reskin, the PDF render) stays exactly as it is today.

01What actually changes

Nothing about the template upload, the reskin prompt, or the PDF render moves. Only the box on the left of the diagram is swapped out.

Today

topic_idchosen from a dropdown of topics already in MySQL
fetch_topic_report_data(topic_id)one fixed query shape: posts, keywords, sentiment counts
Only works for topics that already exist as rows in the database

Proposed

Any free-text question, typed like a chat message
agent_app.ainvoke(...)the same LangGraph agent that answers chat — rewrites the query, generates SQL, runs it, judges the result
Works for anything the chat agent can already answer — not limited to a stored topic

02Four steps to build it

  1. Call the agent in-process, not over HTTP

    /api/chat only streams back the final prose answer — it throws away the structured SQL rows the agent fetched along the way. Call agent_app.ainvoke({...}) directly, the same way chat_endpoint in server.py does, so you get the full result: answer, rows, and sql.

  2. Build REAL_DATA_JSON from rows, not prose

    Package {"query": ..., "answer": result["answer"], "rows": result["rows"], "sql": result["sql"]} in place of fetch_topic_report_data's output. The reskin prompt needs discrete fields to slot into charts and tables — a paragraph of prose alone won't do that reliably.

  3. Hand it to the existing reskin call, unchanged

    render_from_template(template_html, your_data, custom_instructions) already does the "replace sample content, never invent a number" rewrite. It doesn't care where your_data came from.

  4. Render with Playwright, unchanged

    compile_pdf_report_from_template's network-locked Chromium render stays exactly as it is — same CDN allowlist, same PDF output step.

03Before you build

Two tradeoffs worth knowing up front

Latency stacks up
A chat turn already runs query-rewrite → table-selection → SQL-gen → safety-check → execute → judge before you even get to the reskin call, which is itself a full-document LLM rewrite. Expect this path to be noticeably slower than picking an existing topic.
The question has to earn structured data
A vague or chit-chat question won't produce clean rows to fill a template's charts and tables with — the wording needs to be answerable via the database route, not just a conversational one.
