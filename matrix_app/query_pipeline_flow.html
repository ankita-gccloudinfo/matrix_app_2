How a question turns into SQL, then Neo4j Graph Traversal

Every question goes through query_rewriter → query_manager → check_and_run_endpoint_routes → router_node → generate_sql → execute_sql. The endpoint-routes step can end the turn early by calling a matching external API directly; only an unmatched query actually reaches router_node. If MySQL returns 0 rows, content_index_search searches Qdrant for a semantic match, then the new neo4j_search node runs a graph traversal in Neo4j to answer relational questions (connections, followers, ticket chains, police reports) — without going back to MySQL.

🔴

Qdrant (Vector DB) — Used at the content_index_search fallback step. When MySQL returns 0 rows (or a COUNT of 0), the query is embedded with Jina v3 and searched against the content_index collection (4 entity types: CONTENT, INCIDENT, REPORT, TAXONOMY). The matched payload (including unique_topic_id) is forwarded to the new Neo4j step.

🔵

Neo4j (Graph DB) — The new neo4j_search node runs after Qdrant finds relevant topic IDs. It answers relational questions MySQL cannot: "Who follows hate-speech posters?", "Is there a police ticket for this incident?", "Which accounts are connected to this user?" via Cypher traversal across 3M+ nodes.

check_and_run_endpoint_routes — between query_manager and router_node ✅ implemented 🐛→✅ 2 bugs fixed

Third step in the pipeline, right after query_manager writes the standalone query and before router_node ever runs. Unconditional edge in — every turn passes through it. The edge itself is still unconditional (see callouts below for why that's fine now — the fix is a per-turn guard, not a routing change).
ℹ️

Why this sits ahead of router_node: some questions are best answered by calling a live external API in external_endpoints.json (60 registered endpoints) rather than by generating SQL against MySQL or searching a PDF. Checking that first means a genuine API match short-circuits the turn immediately — Option B: call the endpoint directly, no code-gen, no subprocess — instead of getting misrouted into database/pdf_chat and failing there. If nothing matches, the query falls through to router_node completely unchanged, so router_node's own database/pdf_chat logic is untouched by this node's existence.

Why

Some turns aren't a MySQL question or a PDF question at all — they're a live API lookup ("villages in tehsil X", "unread count by subcategory") or an action ("sync the thana matrix"). Sending those into router_node's database/pdf_chat prompt would force a bad-fit route. Checking the endpoint registry first catches these before they're misrouted.

Where

Wired as an unconditional edge straight after query_manager — every standalone query passes through it. Its own conditional edge then either ends the turn (matched) or continues, unchanged, into router_node (no match). See _builder.add_edge("query_manager", "check_and_run_endpoint_routes") and the _endpoint_route_decision conditional edge in ollamaagent2.py.

How

Two LLM passes: Stage 1 loosely gathers plausible candidates from every 30-endpoint batch in parallel (plus a deterministic keyword-overlap safety net); Stage 2 strictly re-validates the merged shortlist and splits it into read vs. write matches. What happens next depends on the count and type of matches — see the diagram and traced examples below.

Fixed — one-sided sentiment/emotion breakdowns were being summarized from the wrong fields. _run_read_endpoints's summarization step (mcp_services.aggregate_records_for_summary) used to never read the endpoint's own pre-computed totals (e.g. sentimentPost's sentimentCounts: {"negative":0,"neutral":9,"positive":0}). It recomputed from the individual post records instead, and detect_summary_fields drops any field with only 1 distinct value ("nothing to break down if every record has the same single value") — so when a topic was entirely one sentiment (all 9 posts "neutral"), sentiment_label itself got discarded as unaggregatable, and the LLM was handed an unrelated field instead (keywords_cloud, broad_category, …) — producing an answer that never mentioned positive/neutral/negative at all.

Fix shipped: aggregate_records_for_summary now builds a precomputed_counts dict straight from each payload's sentimentCounts / primaryEmotionCounts field and merges it ahead of detect_summary_fields's own category detection (field_counts = dict(precomputed_counts); field_counts.update(...)), and the "no aggregatable field" bail-out now checks not category_fields and not precomputed_counts — so an all-one-value field like sentiment_label no longer causes a silent fallback to unrelated fields.

keyword_of_post_maker_node — parallel research branches ✅ implemented

Zooms into the keyword_of_post_maker node above. Runs two independent research branches in parallel, then joins them into one keyword_combination_string. Only reached once the topic is already classified — see the classification diagram below for how an unresolved acronym gets filtered out before it ever reaches this node.
ℹ️

This node no longer resolves ambiguity or talks to the user. An earlier version of this design ran a third "live_search" branch (7 grounded questions + DuckDuckGo) here and could escalate to ask the user directly. That responsibility has since moved entirely to check_query_manager (classification) + query_rewriter's grounded-clarification instance (see the next section) — by the time a query reaches this node, its topic is already known. This node's only job now is building the best possible search combination for that already-known topic.

RETURN
keyword_combination_string
— db_recycle_search Matches the query against curated recycle_search tags via two explicit LLM calls (match the tag, then pull the matched data).
— related_words Generates phonetic variants, common typos, and associated terms for the topic — the fuzzy-matching net that catches misspellings a plain LIKE search would miss. Independent of recycle_search — runs regardless of whether branch 1 found anything.
— join Both branches must complete before this runs. Seeds _generate_keyword_combination_string with the matched keywords + fuzzy variants and produces the final OR-group used in generate_sql's WHERE ... LIKE clause.

Why two branches instead of one recycle_search match: the plain tag match only ever expands what a curated table already knows about. related_words doesn't depend on recycle_search having a matching entry at all — it reasons from the query text itself, so a brand-new topic that was never added to recycle_search still gets real candidate spelling variants.

Why a join call instead of using recycle_search's keywords directly: recycle_search can mis-match unrelated tags, and fuzzy variants can overreach. One call that sees the query plus both branches' output together is what actually decides what's safe to put in the SQL WHERE clause — the same lesson learned from the Kawar Yatra bug (unrelated farmer-union terms getting summed into an unrelated topic's count), applied up front instead of patched after the fact.

Where the acronym-resolution / ask_user logic went: it's no longer here. check_query_manager now deterministically checks the standalone query for an unresolved acronym (e.g. "cjp") against recycle_search before this node ever runs — see the next section. If it's genuinely unresolved, the turn is routed back to query_rewriter's grounded clarification instance instead of reaching here at all.

What always passes

  • A single SELECT …; statement
  • Hindi + English OR'd LIKE search on mixed-language columns
  • LIMIT 200 default on non-aggregated results
  • readUser DB credentials — read-only at MySQL grant level
  • Neo4j uses read-only Cypher (MATCH only, no MERGE/CREATE in queries)

Anti-Fabrication Safety & Token Audit Rules

Ensures no model-hallucinated figures or ungrounded claims reach police distribution.
1. Token Extraction with Attribute Isolation
Extracts standalone numbers, percentages, and multi-word named entities from text nodes only. CSS styling rules, font weights, URLs, and image tags are excluded from false-positive candidate matching.
2. Real Post Text & Quotation Exemption
Verbatim post content, author handles, and source platform URLs from MySQL post_bank records are recognized as verified evidence and protected from redaction.
3. Dynamic Date Normalization & Stoplist Expansion
Expands SQL timestamps into multiple localized date formats (e.g. 2026-09-08 matches "Sep 8, 2026" or "08/09/2026"). The expanded _NAMED_PHRASE_STOPLIST prevents standard analytical terms from being flagged.
4. Fail-Closed Redaction & Playwright PDF Export
Only unverified hallucinations are replaced with <span class="unverified">Not available</span>. Headless Chromium compiles the final sanitized DOM to reports/<report_id>/report.pdf.
